# Review of etl/bagofwords.py

This is a review of `etl/bagofwords.py` generated by Claude Opus 5 on 2026-07-28.
This review has taken into account the review of the remote endpoint `docs/bagofwords-remote-tsi-cts-endpoint-review.md`

## Verdict

The aggregation logic in bagofwords.py is **arithmetically correct**, but it is a **thin, trusting wrapper** around an endpoint that the review shows cannot be trusted as a source of truth. It inherits every tokenization defect described in bagofwords-remote-tsi-cts-endpoint-review.md without compensating for any of them, and it adds a few defects of its own.

I verified the arithmetic against the checked-in data:

```
per-urn files  = 305011 tokens
peryear files  = 305011
_all.txt       = 305011  (43419 types)
_tokensumperyear = 305011
_minmaxyearzipf  = 43419 rows
```

So the merge/rollup pipeline conserves counts exactly. The problem is _what_ it is counting.

---

## 1. Endpoint defects that propagate unmitigated

### 1a. Broken Unicode lowercasing (review §1) — confirmed in your data

The script requests `&lowercase` (pythoncts.py), but because the server has `$multibyte = false`, non-ASCII capitals survive. In \_all.txt:

- **473 tokens still begin with an uppercase letter**
- **207 case-collision groups**, i.e. the same word counted twice:

```
żož 184  /  Żož 21
ṅejo 171 /  Ṅejo 3
żeṅ 129  /  Żeṅ 14
```

This is not cosmetic. It inflates the **type** count and therefore corrupts `_typesumperyear.txt` and the type/token ratio in `_typetokenratioperyear.txt`, and it splits Zipf ranks and first/last-attestation years in `_minmaxyearzipf.txt` (a capitalized sentence-initial form gets its own, wrong, date range).

bagofwords.py never re-lowercases with Python's Unicode-aware `.lower()`, which would fix all 207 groups locally regardless of the server config.

### 1b. Downstream scripts already break because of this

normierowasch.py and `lemmatisierowasch.py` build their own tokens with Python `.lower()` (Unicode-correct) and then validate them against `_all.txt` via `tokencheck()`. The two tokenizers disagree, producing **10 368 lines in \_ERROR.txt**. Of those, **952 are caused purely by the failed server-side lowercasing** — the lowercase form is absent from `_all.txt` because only the capitalized variant was stored:

```
źeden, ńczyń, ńejźij, k’żiſcham, ...
```

So the endpoint's defect is already producing false "unknown token" errors in your own ETL.

### 1c. Punctuation contract is unversioned (review §2) — visible in your data

`’ 544` is the 61st most frequent "word" in your corpus, plus forms like `ſ’tym`, `k’nam`. Since `$replacearr` lives only in the server's un-versioned `config.php`, a server-side config change silently changes your entire dataset with no signal in this repo. bagofwords.py records no provenance (endpoint URL, `version.txt`, punctuation list via the already-available `cts_punctuation()`), so a regenerated dataset is not reproducible or diffable.

### 1d. Surface forms, not normalized words (review §5)

This is fine _by design_ here — `bagofwords` is intentionally the surface-form layer, with normalization handled by normierowasch.py/`lemmatisierowasch.py`. But `_all.txt` is also used as the **validation whitelist** for those layers, which is exactly where the mismatch in 1b bites.

### 1e. Unicode normalization (review §6) — not a problem in practice

I checked: **0 non-NFC tokens and 0 NFC collisions**. Sequences like `muͤ` and `ßeb́e` have no precomposed equivalent, so NFC is a no-op. The review's concern is theoretically valid but does not currently affect this corpus; an `unicodedata.normalize("NFC", …)` guard on ingest would be cheap insurance, not a fix.

## 2. Defects in bagofwords.py itself

### 2a. SQL built by string concatenation (most serious)

bagofwords.py builds every INSERT by embedding remote-derived tokens into double-quoted SQL literals:

```python
vals = '"' + linearr[0] + '",' + linearr[1].strip() + ',"' + dsb_sortkey(linearr[0]) + '"'
cursor.execute("INSERT INTO tokencount(...) VALUES(" + vals + ")")
```

Today there are 0 tokens containing `"` — but only because the server's unversioned `$replacearr` happens to strip it (review §2). If `"` is removed from that list, or an XML entity survives (review §7), this crashes or injects. The same applies to `urn` and `wordbag`. Use parameter binding (`cursor.execute(sql, (token, freq, sortkey))`) — this also removes the need to trust the endpoint's punctuation config.

### 2b. `sanitycheck` is too weak and fires too late

bagofwords.py only checks "2 tab-separated fields per line". It does not check that field 2 is an integer, and it treats an **empty response as a hard error** (`"".split("\n") == [""]`) — the exact "empty passage" case the review flags as untested.

Worse, the output file is opened (and truncated) _before_ the check (bagofwords.py). A failing document leaves a **0-byte `urn_#_*.txt`** behind, which `db()` then happily inserts as a row with `wordbag = "|"` — a document that silently matches nothing instead of being absent. Currently 0 such files exist, so this is latent, not active.

Note also the direct link to review §3: since the endpoint splits only on ASCII space, a tab inside a token would yield 3 fields and cause `sanitycheck` to **discard the entire document** rather than just that token.

### 2c. `_minmaxyearmin.txt` and `_minmaxyearmax.txt` are the same file

bagofwords.py builds both blocks with the identical key:

```python
drange = str(wb_min[token]) + "\t" + str(wb_max[token])
```

Only the iteration order differs (`sorted(wb_min)` vs `sorted(wb_max)`), which affects neither the keys nor the grouping. I diffed them: **156 lines each, identical content**. One of the two is dead output, or the second block was meant to key on something else.

### 2d. Unvalidated remote metadata used as a file path

`year` comes straight from the remote `editions.php` and is used as a filename (bagofwords.py) and later parsed with `int(yearfile.replace(".txt",""))` (bagofwords.py). A non-numeric date (`"18??"`, `"1882-1884"`) crashes `process()`; a value containing `/` or `..` writes outside the target directory. The only guard is `len(year) > 1`.

### 2e. Minor

- `&sort` is requested but Python re-sorts by frequency; the server-side sort is wasted work, and PHP's byte sort — not `dsb_sortkey` — silently determines tie order in `_all.txt`.
- `reset()` never clears `_ERROR.txt`, so the 10 368 lines accumulate across runs and cannot be attributed to a specific run.
- `count = 50` in config.py means the committed dataset is a partial harvest, while `db()` iterates the full inventory. Consistent only because `reset()` wipes the data dir first.
- Frequency ties get no secondary sort key, so Zipf output ordering depends on endpoint response order.

## 3. Answer to the actual question

**Does bagofwords.py make sense given the endpoint review?** Partially. It is correct as an _aggregator_ and wrong as a _consumer_. The review's conclusion is that the endpoint returns "counts of surface strings after limited normalization" whose contract depends on unversioned server config — and bagofwords.py treats that output as already-clean, canonical data: it writes it to disk verbatim, uses it as the whitelist for two downstream ETL stages, and interpolates it into SQL.

Minimum changes to make it defensible, in priority order:

1. Parameterize all SQL in `db()`.
2. Re-lowercase (and optionally NFC-normalize) tokens in Python on ingest — fixes 207 case collisions and 952 downstream errors without touching the server.
3. Validate before writing: check integer frequencies, handle empty responses distinctly, and don't leave truncated files behind on failure.
4. Record provenance per run (endpoint URL, `cts_version()`, `cts_punctuation()`) so a regenerated dataset is diffable.
5. Decide what `_minmaxyearmax.txt` was supposed to be, or delete it.
6. Validate `year` before using it as a path component.
